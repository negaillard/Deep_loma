я хочу уточнить пару моментов по архитектуре. 
смотри: стандартный флоу как будто такой: у нас есть сервер, который связан с БД и файловым сервером. то есть, 
мы имееим ввиду, что есть API, пусть это будет Gateway API. 
далее, человек загружает документ и выбирает подписантов, 
пусть пока что будет так (про последовательную подпись поговорим позднее). 
он делает запрос на апи. Что в это время происходит на сервере: 
документ сохраняется в файловом хранилище, в БД создается сущность документа, 
создаются сущности документ-пользователь (здесь хранится статус этой сущности, дата и еще что то, не помню). 
в это же время формируется сообщение, которое содержит айди документа, список айдишников пользователей, 
которые должны его подписать. кладется в очередь для сервера уведомлений. 
сервер подписей забирает это сообщение, и рассылает уведомления по email для каждого пользователя о том, 
что ему пришли документы на подпись. 
человек заходит в мобильное приложение, делает запрос на gateway api для получения документов на подпись. 
если такие документы есть, он их получает. 
может скачать (отдельный запрос на gateway api для получения именно доокумента). 
выражает намерение подписать (запрос на gateway api), 
на сервере в это время обновляется сущность документ-пользователь. 
когда обновится последняя сущность документ-пользователь связанная с этим документом, 
то будет должно быть сформировано сообщение, которое содержит айдишники пользователей и айди документа. 
сообщение кладется в очередь сервера подписей, сервер подписей забирает это сообщение и делает грязь, 
в конечном итоге, именно он поместит электронные подписи на файловый сервер. 
также он должен отправить сообщение, о том, что все подписи проставлены обратно на основной сервер, 
чтобы были сформированы сущности типа signature, которые уже содержат данные о подписях, 
которые хранятся на файловом сервере. в этом случае документ будет считаться подписанным.

сервер уведомлений опирается на ту же бд.
сервер подписей опирается на ту же бд
